# Режим сервиса Turnable &nbsp;·&nbsp; [🇬🇧 EN](SETUP.md)
Режим сервиса предоставляет уровень управления для запуска нескольких инстансов сервера или клиента Turnable. Он предоставляет протокол управления через Unix сокеты или TCP, позволяя создавать, запускать, останавливать и управлять экземплярами динамически без перезагрузки.

## Гайды для разных платформ
- [Настройка на Windows](WINDOWS_RU.md)
- [Настройка на Linux](LINUX_RU.md)

## Ключевые особенности
- Запуск нескольких инстансов сервера или клиента из одного сервиса
- Динамическое управление инстансами через CLI клиент или программный API
- Опциональное шифрование и аутентификация с использованием ML-KEM-768
- Автоматическое сохранение и автоматический перезапуск инстансов
- Структурированное логирование с потоковой передачей в реальном времени
- Unix или TCP сокеты

## 1. Генерирование ключей шифрования (опционально)
Для безопасной настройки с аутентификацией генерируйте пары ключей ML-KEM-768:
```bash
./turnable config keygen
```

Вы получите вывод вроде:
```
priv_key=whH/S/GPFJ37zGv8n...
pub_key=BWEx0ygunbFJFCrIN...
```

Сервис будет использовать эти ключи для шифрования. Генерируйте отдельные пары ключей для сервера и для каждого клиента, которому нужен доступ.

## 2. Создание конфигурации сервиса
Создайте файл `service.json`:
```json
{
  "unix_socket": "/tmp/turnable.sock",
  "listen_addr": "127.0.0.1:9000",
  "pub_key": "BWEx0ygunbFJFCrIN...",
  "priv_key": "whH/S/GPFJ37zGv8n...",
  "allowed_keys": [
    "client_pub_key_1_base64",
    "client_pub_key_2_base64"
  ],
  "readonly_keys": [
    "panel_pub_key_base64"
  ],
  "persist_dir": "/var/lib/turnable/instances"
}
```

### Поля конфигурации
| Поле           | Обязательно | Описание                                                                   |
|----------------|-------------|----------------------------------------------------------------------------|
| `unix_socket`  | Нет         | Путь к Unix сокету для локальных клиентов (например, `/tmp/turnable.sock`) |
| `listen_addr`  | Нет         | TCP адрес и порт (например, `127.0.0.1:9000` или `0.0.0.0:9000`)           |
| `pub_key`      | Нет         | Публичный ключ ML-KEM-768 сервера для аутентификации (base64)              |
| `priv_key`     | Нет         | Приватный ключ ML-KEM-768 сервера для расшифровки (base64)                 |
| `allowed_keys` | Нет         | Публичные ключи клиентов с полным доступом (base64)                        |
| `readonly_keys`| Нет         | Публичные ключи клиентов только для чтения: list, get, stats, sessions     |
| `persist_dir`  | Нет         | Директория для автозагрузки и сохранения провайдеров и экземпляров         |

> [!NOTE]
> Должно быть установлено хотя бы одно из `unix_socket` или `listen_addr`. Если пара ключей не предоставлена, сервис работает без аутентификации и пишет предупреждение: любой, кто может достучаться до слушателя, получает полный контроль. Если пара ключей есть, а `allowed_keys` нет, подключиться может любой клиент с парой ключей. Клиенты доказывают владение приватным ключом от предъявленного публичного, поэтому утечки одного публичного ключа недостаточно.

## 3. Запуск сервиса
```bash
./turnable service server -c service.json -p /var/lib/turnable/instances
```

Доступные флаги:
```
-c, --config string   путь к JSON файлу конфигурации сервиса (по умолчанию "service.json")
-p, --persist string  директория для сохранения конфигураций экземпляров для автозагрузки
-V, --verbose         включить подробное логирование отладки
```

## 4. Подключение с CLI клиентом
В другом терминале запустите CLI клиент:
```bash
./turnable service client --unix /tmp/turnable.sock
```

Или подключитесь через TCP с аутентификацией:
```bash
./turnable service client \
  --address 127.0.0.1:9000 \
  --pub-key client_pub_key_base64 \
  --priv-key client_priv_key_base64
```

Доступные флаги:
```
-u, --unix string        путь к Unix сокету для подключения
-a, --address string     TCP адрес и порт для подключения
-p, --pub-key string     публичный ключ клиента ML-KEM-768 для аутентификации (base64)
-k, --priv-key string    приватный ключ клиента ML-KEM-768 для аутентификации (base64)
-s, --server-key string  публичный ключ сервиса ML-KEM-768 для закрепления (base64)
```

Передайте `pub_key` сервиса как `--server-key`, и клиент откажется говорить с кем-либо ещё. Без него клиент доверяет любому ключу, который предъявит сервис.

## 5. Управление экземплярами в CLI
После подключения к сервису вы можете использовать команды. Напишите `help` для списка команд.

Провайдеры сохраняются всегда. Экземпляры, созданные с `autostart`, равным `true` (необязательный последний аргумент `start-server` и `start-client`), запускаются снова при старте сервиса, а неудачный запуск или неожиданная остановка повторяются с растущей задержкой от 2 до 60 секунд. Экземпляры без `autostart` возвращаются остановленными.

| Команда | Что делает |
|---|---|
| `stop <id>` | Останавливает экземпляр и удаляет его вместе с сохранённой записью |
| `stop <id> keep` | Останавливает экземпляр, но оставляет его в списке и на диске, после перезапуска сервиса он остаётся остановленным |
| `restart <id>` | Пересобирает экземпляр из сохранённой конфигурации и запускает, работает и для остановленных и упавших |
| `update-instance <id> [name=] [autostart=] [config=] [listen=]` | Меняет экземпляр, новый `config` или `listen` перезапускает его |
| `update-provider <uuid> [name=] [config=]` | Переименовывает провайдер или перезагружает его с новой конфигурацией того же типа |
| `add-route` / `update-route` | Добавляет или заменяет маршрут: `<provider> <id> <address:port> [socket] [transport] [encryption] [name]` |
| `add-user` / `update-user` | Добавляет или заменяет пользователя: `<provider> <uuid> [type] [peers] [allowed_routes] [forceturn]` |

`delete-instance <id>` делает то же, что `stop <id>`. Запрос без ответа в течение 30 секунд завершается тайм-аутом, а соединение остаётся рабочим, так как ответы несут ID своего запроса. Хост, который 5 раз за минуту не прошёл рукопожатие, блокируется на минуту.

## 6. Статистика и управление для панелей
Экземпляры сервера считают трафик по пользователям и ведут учёт живых сессий, поэтому панели не нужно гадать:

| Команда (метод клиента `pkg/service`) | Что делает |
|---|---|
| `stats <id> [collect [ack]]` (`GetStats`, `CollectStats`) | Общие цифры сервера и все замеченные пользователи: трафик, живые туннели, IP подключений, последний визит. С `collect` также возвращает, сколько каждый пользователь передал с предыдущего collect, и обнуляет счётчики; именно это панель опрашивает для подсчёта расхода. С токеном `ack` (`CollectStats`) порция повторяется, пока панель не вернёт её `collect_token`, поэтому потерянный ответ ничего не теряет |
| `sessions <id>` (`ListSessions`) | Живые сессии с пользователем, маршрутом, адресом и трафиком |
| `kick-user <id> <user_uuid>` (`KickUser`) | Закрывает все туннели пользователя, он сможет переподключиться, пока не удалён из провайдера |
| `kick-session <id> <session_id>` (`KickSession`) | Закрывает все туннели сессии |

События открытия и закрытия туннелей рассылаются всем подключённым клиентам как `SessionEvent` (`EventSession` в Go клиенте). Удаление пользователя из провайдера также закрывает его живые туннели. Трафик считается с точки зрения сервера: up — отправленное клиентами в туннель, down — пришедшее обратно.

Ещё не собранный расход сохраняется в директорию persist каждые 30 секунд и при остановке сервиса, поэтому перезапуск его не теряет. Аварийное завершение может потерять до 30 секунд.

Встраиваете сервер напрямую? У `engine.TurnableServer` те же данные доступны методами: `Stats`, `Users`, `User`, `CollectUsage`, `Sessions`, `KickUser`, `KickSession` и `Subscribe`.
